# Opportunity OS · Agent 协作总则

本仓库是**真实信息 → 商业假设 → 客户验证 → 可复用交付**的系统。任何模型输出只能是辅助分析，不是订单和事实。

## 快速导航
- `app/collectors.py`：GitHub 搜索 / Trending / HN / RSS / X / 合规平台数据源、独立频率与失败隔离
- `app/scoring.py`：分类、六维评分、商业 Playbook，不能自行补充虚假付费数据
- `app/db.py`：SQLite、source_configs 独立调度配置、指纹去重、快照
- `app/main.py`：FastAPI API、调度、导出
- `app/static/`：原生 JS/CSS，避免引入不必要的前端依赖
- `tests/test_system.py`：验收测试

## 开发要求
1. 修改前查找依赖链，保持原有 REST API 的兼容性。数据库迁移不能删除已存在字段或数据。
2. 实际网络失败保留上次成功数据。禁用模拟兜底，只有用户主动加载的 `is_demo=1` 才允许样本数据。
3. 不抓取闲鱼、小红书和 1688 的登录/风控页面。仅接受有授权的 RSS/JSON 适配器或人工 CSV/JSON 导入。`LICENSE=UNKNOWN` 不代表可商用；不得用未经授权的账号/API Key 或绕过付费接口。
4. 敏感凭据放 `.env`，不落 DB，不出日志，不进 Git。外部 API 仅用于用户授权的用途。
5. 面向客户的报价必须标注测试价；利润数据只有用户手工记录，不可由模型编造。
6. 前端首选浅色、低噪声、可读性优先。必须显示空白态、错误态、来源链接及时间，前端文本需 HTML escape。
7. 新能力至少增加一个确定性的离线测试并通过 `python -m pytest -q`。有 Node 时还需 `node --check app/static/app.js`。
8. 高风险动作（自动发布、账号授权、付费 API、交易、外发营销）需要用户明确审批，不可偷偷执行。

## Agent 角色
- `scout`：发现新来源、热点及失败定位。
- `analyst`：商业假设、打分证据、合规风险、实验设计。
- `builder`：最小可交付 MVP、自动化验收与数据迁移。
- `growth`：渠道测试、上架文案草稿、咨询转化（不自动发帖）。
- `operator`：真实收入/成本/工时核对与每周复盘。

## 交付完成定义
- 每个 UI 操作真正联动后端并持久化（除明确写为 demo/预览的功能）。
- 有测试结果、有风险说明、有可恢复备份方法。
- 不能把“准备发布”、“计划成交”写成“已真实成交”。
